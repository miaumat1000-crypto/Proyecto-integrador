1. Propósito del proyecto

DataLab integra y aplica los conceptos de Lógica Computacional mediante el desarrollo incremental de una aplicación para procesar registros. Cada entrega incorpora los nuevos temas de la semana y conserva las funcionalidades implementadas anteriormente.

Principio fundamental: no se empieza desde cero en la semana 10. El punto de partida es una base sólida de código que recoge los conocimientos y funcionalidades estudiados hasta la semana 9. Las semanas 10 a 14 amplían y mejoran esa misma solución.

¿Qué se espera construir?

Una aplicación que permita cargar y procesar registros, normalizar y validar sus campos, controlar datos incorrectos, clasificar valores y generar resultados resumidos. El trabajo se realizará paso a paso, siguiendo las versiones definidas para cada entrega.

Enfoque de aprendizaje

  • Reutilizar los conceptos y el código que los estudiantes ya conocen.
  • Incorporar una funcionalidad o mejora central en cada entrega.
  • Comprender la lógica antes de ampliar la solución.
  • Evitar duplicar funciones y mantener el código organizado.
  • Garantizar que cada integrante pueda explicar individualmente el funcionamiento del proyecto.

2. Punto de partida: semanas 1 a 9

El proyecto inicia con una base funcional preparada a partir de los contenidos estudiados hasta la semana 9. Esta base no debe introducir anticipadamente los temas que serán objeto de las entregas posteriores.

Se tendrán en cuenta los conocimientos ya trabajados: variables y tipos de datos, operadores, condicionales, ciclos, contadores, acumuladores, banderas, funciones y estructuras de datos abordadas durante el curso.

Importante: la estructura y el código inicial se definirán respetando exactamente el alcance de las semanas 1–9. Las nuevas herramientas y responsabilidades se incorporarán cuando correspondan a las semanas 10–14.

3. Organización del equipo y roles permanentes

Los equipos estarán conformados por tres estudiantes. Durante las semanas 10 a 14 cada integrante conserva una responsabilidad técnica permanente. Los roles no rotan; las actividades y los archivos asignados evolucionan en cada entrega.

Integrante A · Calidad de datos

Normalización, estandarización y validación

Responsable de la calidad de los registros, independientemente de su fuente.

  • Normalizar identificadores, tipos, unidades y valores.
  • Validar campos obligatorios, formatos y unidades.
  • Identificar registros válidos e inválidos y sus motivos.
  • Crear pruebas de calidad y casos límite.

Archivos principales: src/validation/normalizacion.py, validaciones.py.

Integrante B · Robustez

Manejo de errores y procesamiento

Responsable de la continuidad y confiabilidad del procesamiento.

  • Definir y utilizar excepciones específicas.
  • Controlar errores de conversión, lectura y estructura.
  • Registrar incidencias y evitar que un registro detenga el lote.
  • Integrar validación, clasificación y resumen.

Archivos principales: src/exceptions/errores.py, src/processing/procesamiento.py.

Integrante C · Fuentes

Carga e integración de datos

Responsable de recibir datos desde memoria y archivos externos.

  • Preparar escenarios de entrada en memoria.
  • Implementar lectores CSV, JSON y Excel.
  • Unificar la estructura de salida de los lectores.
  • Probar archivos válidos, vacíos y con estructuras inesperadas.

Archivos principales: src/data/fuentes_memoria.py, lectores.py, carga_datos.py.

Regla de contribución: las tres ramas son complementarias. La integración de A + B + C debe completar el 100 % de la funcionalidad solicitada en cada entrega. La carga se distribuye de forma equilibrada en implementación, pruebas y documentación.

4. Creación del repositorio en GitHub

El docente compartirá el repositorio plantilla. Cada equipo creará un repositorio independiente mediante Use this template → Create a new repository.

  1. Un integrante crea el repositorio del equipo desde la plantilla.
  2. Desde Settings → Collaborators, agrega a los otros dos integrantes.
  3. Los tres clonan el repositorio del equipo y verifican permisos.
  4. Se conserva main como rama estable; no se trabaja directamente sobre ella.
  5. Al comenzar cada entrega se crea una rama de integración semanal y, desde ella, las tres ramas individuales.
No trabajar directamente sobre el repositorio del docente. Cada equipo trabaja en su propio repositorio derivado de la plantilla.

5. Estrategia Git: ramas semanales

Los roles son permanentes, pero las ramas se crean nuevamente en cada semana. Esto permite que los tres integrantes partan de una misma versión y que cada entrega tenga un conjunto identificable de cambios.

main
 └── semana-10
      ├── s10-calidad-datos       (Integrante A)
      ├── s10-robustez            (Integrante B)
      └── s10-fuentes             (Integrante C)

main
 └── semana-11
      ├── s11-calidad-datos
      ├── s11-robustez
      └── s11-fuentes

... repetir hasta semana-14

Flujo obligatorio de integración

  1. Actualizar main y crear la rama de integración semana-XX.
  2. Cada integrante crea su rama individual desde semana-XX.
  3. Trabajar únicamente en los archivos asignados al rol; coordinar cualquier cambio compartido.
  4. Registrar commits pequeños, frecuentes y descriptivos.
  5. Ejecutar pruebas individuales y abrir Pull Request hacia semana-XX.
  6. Revisar e integrar los tres Pull Requests; resolver conflictos sin sobrescribir el trabajo de otros.
  7. Ejecutar pruebas de integración y abrir Pull Request de semana-XX hacia main.
  8. Verificar que main queda ejecutable y conserva las funcionalidades anteriores.

6. Entregas progresivas del proyecto

DataLab es un único producto. Cada versión conserva lo anterior y agrega las funcionalidades de la semana. Los tres roles contribuyen en cada entrega.

Semana 10 · PI1

Normalización y validación

DataLab v1.0

A: normalizar y validar registros. B: integrar estados de procesamiento válido/inválido. C: preparar fuentes y casos de prueba en memoria.

Archivos: normalizacion.py, validaciones.py, procesamiento.py, fuentes_memoria.py.

Aceptación: registros normalizados, válidos e inválidos separados con motivos; clasificación centralizada reutilizada.

Semana 11 · PI2

Manejo de errores

DataLab v1.1

A: motivos y mensajes de validación precisos. B: excepciones, reporte de errores y continuidad por registro. C: escenarios de fuentes defectuosas.

Archivos: `validaciones.py`, `errores.py`, `procesamiento.py`, escenarios y pruebas de entrada.

Aceptación: un registro defectuoso no detiene el lote; los errores quedan identificados.

Semana 12 · PI3

Carga de archivos

DataLab v1.2

A: calidad de registros provenientes de archivos. B: controlar errores de lectura y conversión. C: lectores CSV, JSON y Excel y salida homogénea.

Archivos: `normalizacion.py`, `validaciones.py`, `errores.py`, `lectores.py`, `carga_datos.py`.

Aceptación: los tres datasets se cargan y procesan con el contrato común.

Semana 13 · PI4

Refactorización

DataLab v1.3

A: eliminar duplicidad en reglas de calidad. B: refactorizar procesamiento y trazabilidad. C: mejorar lectores y carga uniforme.

Archivos: módulos de `validation/`, `exceptions/`, `processing/` y `data/` según rol.

Aceptación: se conservan los resultados de v1.2 y mejora la mantenibilidad.

Semana 14 · PI5

Pruebas y sustentación

DataLab v1.4

A: pruebas de calidad. B: pruebas de errores e integración. C: pruebas de lectores y fuentes.

Archivos: `tests/test_calidad.py`, `test_errores.py`, `test_lectores.py`, `test_integracion.py` y documentación.

Aceptación: pruebas completas, versión estable, evidencia Git y sustentación individual.

Distribución equilibrada: la carga de referencia por semana será aproximadamente A 33 %, B 33 % y C 34 %, ajustada según la complejidad de las tareas. La suma de los tres aportes debe completar el 100 % de la funcionalidad.

9. Contratos de integración

Todos los módulos intercambian registros con las claves id, tipo, valor y unidad. Los lectores entregan la estructura común; el rol A normaliza y valida; el rol B coordina el procesamiento y reporta errores.

Resultado común:
{
  "registros_validos": [],
  "registros_invalidos": [],
  "errores": [],
  "resumen": {}
}
  • Los lectores no clasifican ni duplican validaciones.
  • La normalización devuelve una copia y no altera la entrada original.
  • La validación devuelve estado y lista de motivos.
  • Un error individual no debe detener el lote completo.
  • La interfaz consume el servicio de aplicación; no contiene reglas de negocio.

10. Evaluación del proyecto: código y sustentación

40 % de la nota

Código entregado y funcionando

Se evalúa el producto integrado y ejecutable, cumplimiento de funcionalidades, pruebas, calidad del código, integración de las tres ramas, commits y trazabilidad del trabajo.

60 % de la nota

Sustentación

Se evalúa la comprensión individual y grupal. Cada estudiante debe explicar su rol, los módulos desarrollados, decisiones técnicas, pruebas, integración y el flujo completo de DataLab.

Condición explícita: entregar código que funciona equivale al 40 % de la nota. El 60 % restante corresponde a la sustentación. Un producto funcional no sustituye la demostración de comprensión individual.

11. Criterios de aceptación del código (40 %)

  • Funcionalidad integrada: los aportes de A, B y C completan el 100 % de la funcionalidad semanal.
  • Continuidad: se conservan las funcionalidades de las versiones anteriores.
  • Pruebas: existen casos correctos, incorrectos y límite según el alcance semanal.
  • Calidad: módulos con responsabilidades claras, sin duplicación de lógica.
  • Git: ramas semanales, commits descriptivos, Pull Requests y revisión.
  • Ejecutabilidad: el proyecto se instala y ejecuta siguiendo el README.

12. Criterios de sustentación (60 %)

  • Comprensión individual: explica el código que desarrolló y puede justificar sus decisiones.
  • Comprensión global: explica cómo se conectan los tres roles y cómo fluye la información.
  • Demostración: ejecuta escenarios de funcionamiento y explica resultados.
  • Pruebas y errores: interpreta casos válidos, inválidos y fallos controlados.
  • Git y colaboración: explica sus ramas, commits, Pull Requests y contribución.
  • Capacidad de análisis: responde preguntas y propone cómo resolver variaciones del problema.
La sustentación puede incluir preguntas individuales sobre módulos desarrollados por otros integrantes para comprobar que cada estudiante comprende el producto completo, sin desconocer su responsabilidad específica.
